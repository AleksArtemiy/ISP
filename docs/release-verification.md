## Исправлено

Защищены скачивание и хранение приватных файлов; проверяются структура и
ограничения загрузок. Устранены open redirect и DOM-интерполяция имён файлов.
Обычный edit больше не обходит обязательный отчёт при завершении.
Сохранены атомарные операции и компенсирующая очистка новых файлов.

Исторические связи предписаний, загрузчиков и нарушений защищены PROTECT.
Прикладное удаление пользователя заменено деактивацией; запрет удаления
связанных справочников показывается штатно, включая AJAX.

ADMIN отделён от системных флагов Django по подтверждённой модели владельца.
Прикладной администратор не может присвоить системные права через сброс
пароля системного пользователя. Применяются штатные password validators,
общая PostgreSQL-защита попыток входа и POST-only logout. Подсказки нарушений
для директора ограничены его учреждением; коды системных ролей защищены в
Django Admin от удаления и обычного редактирования.

Дашборды и updater используют единый расчёт десяти рабочих дней. Запросы
дашборда не растут линейно с числом учреждений. Реестр получил надзорный орган
и диапазоны дат; scope директора не расширяется фильтром, пагинация кодирует
и сохраняет параметры. README, ПМИ, CI и deployment/runbook обновлены.

Из Git исключён db.sqlite3 с сохранением физического файла. В текущем дереве
не отслеживаются .env, media и runtime-артефакты. Локальный .env не читался;
все Django-проверки выполнялись с PYTHON_DOTENV_DISABLED=1. Реальные рабочие
данные, пути вложений и дополнительные таблицы не удалялись и не перепривязывались.
История Git не переписывалась.

## Требует инфраструктурной проверки

1. Существующая схема: в снимке django_admin_log связан с auth_user, а текущая
   модель с users. Старые идентификаторы и данные нужно исследовать на копии
   и согласовать план. Дополнительные таблицы считаются гипотезой о прошлом
   состоянии, не доказанно ненужными данными. Типы дат и nullable-колонки также
   требуют сверки. Рабочая БД не изменялась.
2. Реальный HTTPS/reverse proxy, правильный REMOTE_ADDR, ограничение размера
   и частоты запросов, изоляция приватного media, непривилегированная роль БД,
   автоматический restart и доступность локальных/внешних ресурсов интерфейса.
3. Реальный scheduler с логами и контролем пропущенного запуска. Подготовлены
   примеры systemd и Windows Task Scheduler; настройки сервера не устанавливались.
4. Ежедневный backup PostgreSQL+media, off-site storage, retention ≥30 дней,
   мониторинг и восстановление на сервере в пределах четырёх часов. Локальный
   drill относится только к синтетическим данным, не к резервной копии Заказчика.
5. Ручная ПМИ и нагрузка с реальными объёмами/сохранением. Отдельно оценить
   задержку массового входа при production-хэшировании.
6. Формально закрепить модульный объём этапа 1 и принять уточнение ADMIN в
   приёмочных документах. Подтверждение владельца для реализации уже получено.
