# Программа и методика проверки первого этапа Реестра предписаний

Документ применяется к release candidate этапа 1. Исходная
«Методика_испытаний.docx» сохранена. Эта редакция содержит актуальные сценарии
авторизации, безопасности и развёртывания после hardening; прежние отметки
Pass не переносятся на новый release. Формат — Markdown, пригодный для
переноса в Word и хранения вместе с кодом.

## Объём и критерий решения

Проверяются авторизация, пользователи и роли, учреждения и справочники,
предписания, нарушения, вложения, завершение, дашборды, административная
панель, фильтры, сроки, миграции и эксплуатационная подготовка.
Полноценный аудит, финансирование, email и прикладной backup отложены на
этап 2, OCR — на этап 3. Внешний backup PostgreSQL/media обязателен уже сейчас.
Заказчик должен подтвердить этот объём отдельным планом/протоколом, поскольку
полное ТЗ не содержит подробной модульной разбивки по этапам.

GO для опытной эксплуатации возможен только при отсутствии открытых P0/P1,
успешных автоматических и ручных проверках, подтверждённых TLS/proxy,
scheduler, backup/restore, согласованной существующей БД и актуальном CI.
Пропущенная или невыполнимая проверка получает «не проверено», а не Pass.

## Предусловия и фиксация стенда

В протоколе фиксируют release SHA (`git rev-parse HEAD`), ОС, Python, Django,
PostgreSQL, параметры сервера без секретов, объём тестовых данных, дату,
исполнителя и использованный сценарий: чистая установка либо upgrade копии.
Рекомендуемый проверенный стек: Python 3.14, Django 6.0.9, PostgreSQL 18.

1. Развернуть отдельную PostgreSQL и отдельный приватный media-каталог.
2. Выполнить migrate, check, makemigrations --check --dry-run, test,
   collectstatic, schema_preflight и check --deploy.
3. Проверить создание трёх системных ролей без ручных INSERT.
4. Создать два учреждения А/Б, надзорный орган, предписания А/Б и пользователей.
5. Для production-сценариев использовать HTTPS, реальный reverse proxy и
   непривилегированную роль приложения; сохранить логи команд и CI URL.

## Тестовые пользователи

| Учётная запись | Настройка | Ожидание |
|---|---|---|
| Анонимный | Без сессии | Защищённые разделы направляют на вход |
| ADMIN | Role.code=ADMIN, is_staff=False, is_superuser=False | Прикладное управление и все учреждения |
| COMMITTEE | Role.code=COMMITTEE | Все учреждения в бизнес-функциях |
| DIRECTOR А | Учреждение А | Только А |
| DIRECTOR Б | Учреждение Б | Только Б |
| Неизвестная роль | Нераспознаваемый code | Отказ по умолчанию |
| Директор без учреждения | DIRECTOR, institution=NULL | Отказ |
| Неактивный | is_active=False | Вход запрещён без раскрытия существования |
| Django-superuser | Системные флаги | Системная и прикладная панели |

Пароли тестовых пользователей задаются на стенде, не используются для
production. Семантика ADMIN согласована владельцем: роль не повышает
is_staff/is_superuser. Условия TC-A3/TC-ADM исходной ПМИ и спецификации
применяются с этим уточнением; `/admin/` остаётся системным уровнем Django.

## Ручная приёмка интерфейса

Проверить создание/редактирование учреждения, типа, надзорного органа и
пользователя через модальные окна и обычные страницы; ошибки формы должны
оставаться видимыми и исправляться без потери полей. Убедиться, что удаление
пустой справочной записи работает, связанной — показывает понятный отказ.
Проверить обычный выбор файлов, drag-and-drop, удаление выбранного файла,
пять вложений, неуспешное сохранение и последующий успешный повтор.
Проверить кнопку отмены и возврат в исходный разрешённый раздел.

В имени тестового файла использовать HTML-подобный текст и убедиться, что
он остаётся текстом в DOM. На Windows знаки < и > запрещены в локальных
именах: такой сценарий проверяют через File API тестового браузера либо на
ОС, которая допускает эти имена. Не записывать потенциальный HTML в innerHTML.

Проверить современные браузеры, мобильную ширину, навигацию, русские
сообщения и цветовые статусы. Для дашборда создать просроченное, истекающее,
выполненное и далёкое предписание, вручную сверить карточки и статистику.

## Нагрузка

На изолированном стенде выполнить scripts/load_stage1.py: 30 отдельных
сессий, 22 синтетических учреждения, 110 предписаний, восемь потоков Waitress.
Сценарий включает вход с CSRF, dashboard → list → detail, два прохода.
Фиксировать p50/p95/p99, ошибки и характеристики сервера. Требование к
основным страницам — не более трёх секунд; для локального прогона контролируется
p95, итоговая приёмка дополнительно рассматривает худшие случаи.
Тест не загружает CSS/изображения и не проверяет TLS/reverse proxy.
На целевом сервере повторить с реальными объёмами и браузерными ресурсами,
включить создание/редактирование и сохранение вложений до 10 МиБ.
Проверить сохранение до трёх секунд и появление записи у Комитета не позднее
15 секунд при обновлении страницы. Фактические значения заносятся в протокол.

## Эксплуатационные проверки

1. HTTPS/TLS 1.2+, сертификат, redirect HTTP→HTTPS, secure cookies, CSRF,
   ALLOWED_HOSTS, origin, private media и закрытый backend-порт.
2. Приложение подключается непривилегированной ролью PostgreSQL; пароль и
   SECRET_KEY не находятся в Git и не попадают в логи.
3. Scheduler реально выполняется, сохраняет exit code/лог и сообщает о сбое.
4. Ежедневный согласованный backup PostgreSQL+media с retention ≥30 дней,
   off-site хранением и мониторингом; восстановление укладывается в четыре часа.
5. Проверка существующей БД на копии и согласование расхождений старого журнала.
6. CI проходит на release SHA; README воспроизводим новым разработчиком.
7. Зафиксировать ошибочные/пропущенные сценарии и решение GO/NO-GO; подписать
   акт только после выполнения обязательных проверок на целевом стенде.
