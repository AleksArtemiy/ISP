## Фактический результат миграционных проб

`migrate --noinput` на отдельной копии останавливается на
`institutions.0001_initial`: `relation "institution_types" already exists`.

`migrate --fake-initial --noinput` на другой копии помечает начальные
institutions/contenttypes как FAKED, затем останавливается на
`contenttypes.0002_remove_content_type_name`: колонка `name` уже отсутствует.
Это ожидаемо для структуры, снятой после миграций, но без их данных.
Нельзя лечить это последовательным угадыванием `--fake`: так можно скрыть
пропущенные преобразования и сохранить неверные FK/типы.

`schema_preflight` корректно сообщает о трёх отсутствующих таблицах и
неверной цели FK журнала. Эта команда проверяет ограниченный набор условий,
а полное структурное сравнение выполняет репетиционный скрипт.

## Порядок подготовки переноса

1. Получить согласованную полную резервную копию PostgreSQL и media из одного
   окна остановленной записи. Сохранить неизменяемый исходник, SHA-256,
   версии приложения/СУБД и фактическую историю `django_migrations`.
2. Восстановить в изолированный контур. Запустить
   `deploy/legacy-data-audit.sql`: транзакция READ ONLY, только счётчики и
   определения constraints. Нулевые результаты на schema-only стенде
   подтверждают исполнимость SQL, но не качество реальных данных.
3. Сопоставить дополнительную и текущую модели данных: учреждения,
   сотрудники/пользователи, предписания, нарушения и статусы. Отдельно
   составить проверяемую карту `auth_user.id → users.id` для журнала;
   неоднозначные записи сохранить и вынести на решение владельца.
4. Согласовать исходный часовой пояс, обработку пустых обязательных полей,
   email-дублей, неизвестных ролей и исторических COMPLETED без отчёта.
   Не назначать роль ADMIN, не создавать отчёты и не подставлять даты
   автоматически ради прохождения ограничений.
5. По фактической истории выбрать один проверяемый путь: последовательное
   обновление копии либо перенос в новую БД с чистой release-схемой.
   При переносе сохранить ID/внешние ключи/историю и отдельно архивировать
   все дополнительные таблицы. Старую БД сохранить для отката.
6. Подготовить преобразователь под утверждённые правила, выполнить dry-run
   и перенос на копии. Сверить количество строк, связи, статусы, даты,
   файлы и их хеши, sequence/identity после явного переноса ID. Проверить
   разрешения, миграции, системный журнал и реальные физические FK.
7. Прогнать приёмку и полное восстановление копии. До переключения получить
   одобрение конкретного результата и окна работ; затем повторить процедуру
   на свежей согласованной копии с планом возврата.

Конкретный преобразователь реальных данных пока не может быть достоверно
завершён: отсутствуют сами записи, история миграций и решения по неоднозначным
соответствиям. Это ограничение исходных материалов, а не подтверждение
потери или повреждения данных.

## Повторение структурной репетиции

Сначала создать чистую синтетическую БД `scripts/verify_stage1.py`. Затем
на отдельном локальном кластере проекта выполнить:

```text
python scripts/rehearse_legacy_schema.py --schema <проверенный-minobr_schema.sql> --reference-db <stage1_clean_...> --pg-bin <каталог-bin-PostgreSQL>
```

Скрипт проверяет идентичность кластера по `postmaster.pid`, использует только
127.0.0.1:55432, создаёт новые уникальные `stage1_schema_*`, сохраняет их и
логи. SQL-файл выполняется psql, поэтому до импорта его содержимое должно
быть проверено. Это инструмент репетиции, не команда обновления рабочей БД.
