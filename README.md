## Назначение

ИС «Реестр предписаний» автоматизирует работу с предписаниями надзорных органов:

- ведение единого реестра предписаний;
- привязку предписаний к учреждениям и надзорным органам;
- хранение перечня нарушений;
- контроль сроков исполнения;
- прикрепление подтверждающих документов;
- отображение сводной статистики;
- разграничение данных по ролям пользователей;
- администрирование пользователей и справочников.

В проекте предусмотрены отдельные приложения для финансирования, уведомлений и аудита, однако их бизнес-логика в текущей версии ещё не реализована полностью.

## Роли пользователей

### Администратор

В коде определяется прежде всего через `is_superuser`.

Доступные возможности:

- пользовательская административная панель `/admin-panel/`;
- создание, редактирование и удаление пользователей;
- включение/блокировка пользователей через `is_active`;
- изменение пароля пользователя через форму редактирования;
- управление учреждениями;
- управление типами учреждений;
- управление надзорными органами;
- доступ к стандартной Django Admin `/admin/`.

### Комитет образования

Пользователь с соответствующей ролью получает доступ к общему дашборду и данным всех учреждений.

В текущей реализации доступны:

- сводная статистика;
- карточки учреждений;
- общий реестр предписаний;
- просмотр нарушений;
- создание и редактирование предписаний;
- фильтрация реестра.

### Директор учреждения

Пользователь привязывается к конкретному `Institution`.

В текущей реализации:

- дашборд ограничивается своим учреждением;
- список предписаний фильтруется по учреждению;
- учреждение и автор могут автоматически подставляться при создании предписания;
- редактирование чужого предписания блокируется проверкой доступа.

## Реализованные возможности

### 🔐 Авторизация и пользователи

Используется кастомная модель пользователя `apps.accounts.models.User`:

- email используется вместо `username`;
- пароль хранится через стандартный механизм хеширования Django;
- ФИО и телефон;
- роль пользователя;
- привязка к учреждению;
- `is_active`, `is_staff`, `is_superuser`;
- `last_login`, дата создания и дата обновления.

### 🏫 Учреждения

Модель учреждения содержит:

- полное наименование;
- краткое наименование;
- адрес;
- тип учреждения;
- даты создания и обновления.

Тип учреждения вынесен в отдельный справочник `InstitutionType`.

### 📋 Предписания

Для предписания хранятся:

- номер;
- учреждение;
- надзорный орган;
- пользователь-создатель / ответственный;
- дата выдачи;
- срок исполнения;
- статус;
- даты создания и обновления.

Статусы модели `Order`:

| Код | Название |
|---|---|
| `NEW` | Новое |
| `IN_PROGRESS` | В работе |
| `COMPLETED` | Выполнено |
| `OVERDUE` | Просрочено |

Реестр поддерживает:

- поиск по номеру;
- фильтрацию по статусу;
- фильтрацию по учреждению для Комитета/администратора;
- сортировку по дате создания, сроку и номеру;
- пагинацию по 20 записей;
- отображение ответственного;
- просмотр карточки предписания.

### ⚠️ Нарушения

Нарушения хранятся отдельно в `violations`.

Связь между предписаниями и нарушениями реализована через промежуточную таблицу `order_violations`, что позволяет использовать связь «многие ко многим».

### 📎 Вложения

К предписанию можно прикреплять документы.

Текущие ограничения загрузчика:

- не более **5 файлов** за одну операцию;
- размер каждого файла — не более **10 МБ**;
- разрешённые расширения:
  - `.pdf`;
  - `.doc`, `.docx`;
  - `.xls`, `.xlsx`;
  - `.jpg`, `.jpeg`, `.png`.

Файлы сохраняются в `MEDIA_ROOT` по структуре:

```text
media/
└── prescriptions/
    └── YYYY/
        └── MM/
            └── DD/
```

В БД сохраняются оригинальное имя, путь, пользователь, загрузивший файл, и дата загрузки.

### 📊 Дашборды

**Дашборд Комитета** рассчитывает данные через Django ORM:

- общее количество предписаний;
- количество просроченных;
- количество исполненных;
- количество предписаний с приближающимся сроком;
- процент исполнения;
- количество новых записей за последние 30 дней;
- показатели по каждому учреждению;
- общий реестр предписаний.

**Дашборд учреждения** отображает:

- предписания конкретного учреждения;
- количество исполненных;
- количество просроченных;
- количество предписаний с приближающимся сроком;
- нарушения и ответственных.

Файл `apps/dashboard/mock_data.py` остаётся в репозитории как ранняя заготовка, однако текущие представления дашбордов получают основные данные через ORM.

## Модель данных

Проект работает с существующей схемой PostgreSQL. Для значительной части моделей указано `managed = False`: Django использует эти таблицы, но **не создаёт и не изменяет их через миграции**.

| Таблица | Django-модель | Управляется Django |
|---|---|:---:|
| `roles` | `Role` | Нет |
| `users` | `User` | Да |
| `institution_types` | `InstitutionType` | Нет |
| `institutions` | `Institution` | Нет |
| `supervisory_authorities` | `SupervisoryAuthority` | Нет |
| `orders` | `Order` | Нет |
| `violations` | `Violation` | Нет |
| `order_violations` | `OrderViolation` | Нет |
| `files` | `File` | Нет |
| `funding_requests` | ORM-модель отсутствует | — |
| `audit_logs` | ORM-модель отсутствует | — |

> Перед первым запуском на чистой БД необходимо создать таблицы с `managed=False` по схеме БД проекта. Одного `python manage.py migrate` для развёртывания всей предметной схемы недостаточно.

Дополнительно кастомный `User` наследуется от `PermissionsMixin`, поэтому Django использует стандартные механизмы групп и разрешений.

## Быстрый запуск

### 1. Клонировать репозиторий

```bash
git clone https://github.com/AleksArtemiy/ISP.git
cd ISP
```

### 2. Создать виртуальное окружение

Windows:

```powershell
py -3.12 -m venv .venv
.venv\Scripts\activate
```

Linux / macOS:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
```

### 3. Установить зависимости

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Подготовить PostgreSQL

Создайте БД проекта, например:

```sql
CREATE DATABASE minobr;
```

После этого необходимо создать существующие предметные таблицы, отмеченные выше как `managed=False`.

> Репозиторий в текущем состоянии не содержит отдельного SQL-скрипта полного развёртывания предметной схемы. Используйте актуальную схему БД проекта.

### 5. Настроить подключение к БД

Текущая конфигурация находится в:

```text
config/settings.py
```

Для локальной разработки укажите свои параметры `NAME`, `USER`, `PASSWORD`, `HOST`, `PORT`.

**Не используйте и не публикуйте реальные production-пароли в репозитории.** Для промышленного развёртывания параметры БД и `SECRET_KEY` следует вынести в переменные окружения.

### 6. Выполнить Django-миграции

После создания требуемых unmanaged-таблиц:

```bash
python manage.py migrate
```

### 7. Создать администратора

```bash
python manage.py createsuperuser
```

В проекте используется email как логин.

### 8. Запустить сервер разработки

```bash
python manage.py runserver
```

После запуска:

```text
http://127.0.0.1:8000/
```

## Работа с файлами

В режиме разработки Django обслуживает `MEDIA_URL` из `MEDIA_ROOT`.

Каталог `media/` добавлен в `.gitignore`, поэтому пользовательские документы не должны попадать в Git.

Для production-среды рекомендуется:

- отдавать media-файлы через веб-сервер или отдельное файловое хранилище;
- ограничить права доступа к каталогу;
- выполнять резервное копирование;
- дополнительно проверять MIME-тип, а не только расширение;
- при необходимости добавить антивирусную проверку загружаемых документов.

## Текущие ограничения и технический долг

README намеренно фиксирует эти пункты, чтобы не смешивать текущий код с целевыми требованиями системы.

### Финансирование

`apps/funding/` существует, но:

- `models.py` не содержит модели заявки;
- CRUD заявок отсутствует;
- в дашборде финансирование сейчас подставляется как `0`;
- список `funding_requests` передаётся как пустой.

Таблица `funding_requests` предусмотрена проектной схемой БД, но ещё не подключена к Django ORM.

### Аудит

`apps/audit/` пока является каркасом.

В текущем коде нет:

- модели `AuditLog`;
- записи изменений пользователей;
- просмотра истории изменений предписания;
- пользовательского интерфейса журнала аудита.

Таблица `audit_logs` предусмотрена проектной схемой БД.

### Уведомления

`apps/notifications/` пока не содержит механизма отправки email.

Отсутствуют:

- почтовая конфигурация приложения;
- фоновые задачи/планировщик;
- уведомления о новых предписаниях;
- предупреждения о приближении срока;
- уведомления о просрочке.

Иконка уведомлений в интерфейсе пока не означает наличие серверной системы уведомлений.

### Статусы и сроки

В модели хранятся четыре статуса: `NEW`, `IN_PROGRESS`, `COMPLETED`, `OVERDUE`.

Сейчас:

- отдельного сохраняемого статуса `EXPIRING` нет;
- приближение срока вычисляется при формировании дашборда;
- порог в текущем коде — **14 календарных дней**;
- автоматическая management-команда обновления статусов отсутствует.

### Завершение предписания

Обработчик завершения устанавливает `COMPLETED`, однако текущий код ещё не требует обязательной загрузки итогового отчёта именно в момент завершения.

### Разграничение доступа

В дашбордах и операциях редактирования присутствуют ролевые проверки. При дальнейшем развитии проекта следует унифицировать защиту всех class-based views реестра через `LoginRequiredMixin`/общие permission-mixins и централизовать проверку ролей.

### Роли

Определение роли «Комитет» в нескольких местах основано на строковом сравнении `role.name`. Желательно заменить это стабильным кодом роли или перечислением, чтобы исключить зависимость от языка и регистра.

### Конфигурация

Текущий `settings.py` ориентирован на разработку:

- `DEBUG = True`;
- `ALLOWED_HOSTS` не настроен;
- параметры БД и `SECRET_KEY` необходимо вынести из исходного кода;
- `LANGUAGE_CODE` и `TIME_ZONE` следует привести к целевой среде эксплуатации.

### База данных

В репозитории присутствует `db.sqlite3`, однако активная конфигурация `DATABASES` использует PostgreSQL. SQLite-файл не является источником данных для текущей конфигурации.

### Тесты

Автоматические Django-тесты пока не реализованы.

## Подготовка к промышленному развёртыванию

Перед размещением системы на сервере необходимо как минимум:

- вынести секреты и параметры подключения к БД в переменные окружения;
- установить `DEBUG = False`;
- задать `ALLOWED_HOSTS`;
- настроить HTTPS;
- настроить WSGI-сервер и reverse proxy;
- организовать обслуживание `static` и `media`;
- настроить регулярное резервное копирование PostgreSQL и пользовательских файлов;
- реализовать аудит критических действий;
- реализовать email-уведомления;
- добавить автоматические тесты;
- проверить права доступа для каждого маршрута;
- выполнить `python manage.py check --deploy`;
- подготовить отдельный способ первоначального создания схемы БД.

## Краткий итог

Текущая версия проекта уже содержит рабочую основу системы:

- кастомную авторизацию;
- пользователей, роли и учреждения;

- вложения;

README описывает **реализованное состояние проекта**, а не полный объём функций, запланированных техническим заданием.
